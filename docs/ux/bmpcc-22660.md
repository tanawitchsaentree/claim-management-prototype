Where it is built: Claim Overview "Close Claim", Sections "Close N sections", Claims list "Close N claims".

## Who

Primary: claim handler.
- Owns 40 to 120 open claims. Assumption, typical commercial portfolio.
- Knows the claim story, but not every task other teams opened on it (Recovery, Finance, Legal).
- Juggles payments, reserves, broker mails and deadlines at the same time.
- Closes one claim a few times a week. Closes several sections of one claim at the end of a settlement.

Secondary: claims manager cleaning up a team backlog.
- Closes many claims at once from the Claims list, for example after a reserve review. Confluence 3229970000 shows this need exists today, done by IT.
- Knows the claims only from the list, not from the inside.
- Does this rarely, maybe once a month. Assumption.

## Story

As a claim handler I want to close a claim, or several of its sections, in one go, and see exactly what still stops it, so that my open list is honest and reserves are released without me hunting through tabs.

As a claims manager I want to close a set of finished claims in one action and get a clear result per claim, so that I can clean up a backlog without opening each claim.

Real-world triggers
- Final payment went out and the handler wants to wrap up. Confluence 3238063411 says the direction is automatic closure after the final payment when nothing else blocks.
- A section is settled and the rest of the claim is too.
- A manager sees dormant claims in the list and wants them gone.

## Journey A: close one claim (Claim Overview)

1. Trigger. Handler opens Claim Overview after the last payment.
   - Sees: status Open, "Close Claim" button.
   - Believes: "this one is done".
   - Does: presses Close Claim.
   - Feels: confident, wants it over with.
2. Blockers.
   - Sees: a list of what still stops closure, open tasks with type and domain (AC-01), open sections.
   - Believes: "I thought I was done. Whose task is that?"
   - Does: reads, then goes to the place that fixes it.
   - Feels: interrupted, maybe annoyed. Needs the reason to feel fair and fixable.
3. Fix and come back.
   - Sees: Task manager or Sections.
   - Does: completes, cancels or defers the task (AC-02 says those no longer block), closes the section.
   - Feels: wants a short way back to the claim.
4. Checklist.
   - Sees: pre-closure checklist, all ticked, "No open tasks" first (AC-02).
   - Does: Continue.
5. Reason and retention.
   - Does: picks a reason, keeps default 10 year retention or sets a date.
6. Confirm.
   - Sees: statements to confirm, then the final button.
   - Believes: "this is the point of no return". Reopen exists, but it is effort.
   - Does: confirms.
7. Done.
   - Sees: a toast, status Closed, closure date, reason, retention, Reopen button.
   - Feels: relief.

## Journey B: close several sections (Sections)

1. Handler opens Sections after settlement.
2. Ticks the rows, or the header box (AC-03). Sees a bar "N sections selected" with Close and, if needed, Reopen.
3. Presses Close. Sees a short check spinner, then each section as Ready to close or Stays open with the reason (AC-03, AC-04).
4. Continue with the ready ones. Sees the names that will close and the ones that stay open, one reason, one confirmation (AC-04).
5. Presses Close. Sees a spinner, then a result per section (AC-04). If one failed, "Try again" for just that one (AC-06).
6. Done. Back on the table, statuses updated, selection gone.
7. If nothing can close: only Cancel, no override (AC-07).

## Journey C: close several claims (Claims list)

1. Manager filters the list, ticks claims.
2. Presses "Close N claims". Each claim is checked, open tasks listed with type and domain (AC-05).
3. Continue with the ready ones, one reason, default retention for all (AC-05 decision).
4. Result per claim, then back to the list with updated statuses.

## Pain points

- PP1 Surprise blocker. The handler thinks the claim is done, then learns other teams still have tasks on it. Source: AC-01, Confluence 3238063411 open point on tasks.
- PP2 Fix means leaving. Every blocker lives on another page. Losing the way back costs minutes and context.
- PP3 "Cancel or defer" must be possible where the task lives, or the wording promises something the handler cannot do. Source: AC-01 wording.
- PP4 Counts that do not match. Selecting 4 and closing 3 must never look like 4 will close.
- PP5 Partial success. In bulk, some close and some do not. The user must know which, and that the others are unchanged (AC-04).
- PP6 Technical failure mid-batch. The user must know nothing broke on the others and can retry one (AC-06).
- PP7 False promises. A message must never say "can now be closed" when something still blocks.
- PP8 Irreversible feeling. Closure releases reserves and closes tasks (Confluence 3238063411 §3). The confirm step must name what is being closed.
- PP9 Selecting things that are already closed. Bulk lists mix states. Closed items should not look like errors.
- PP10 Automatic closure is silent. If the system closes, or refuses to close, the handler must be told (walkthrough step 1).
- PP11 Permission. Only a handler allowed to change status may close (Confluence 3238063411 §3).

## Needs per moment

- Before: the Close action is where they expect it, and selection shows a count with the item kind.
- Blocked: every blocker named, with the item (which task, which section) and a link to fix it.
- Leaving to fix: a way back to the claim that is visible on the target page.
- Confirm: the exact items that will close, the reason, and what stays open.
- During: a spinner with a plain label, buttons locked.
- After: a toast or result that says what happened, items updated in place, selection cleared.
- Error: what failed, that the rest is safe, one retry action.

## Checks (owner's rules, apply to every step)

- Signal: after every action something visible changes (toast, status, result list).
- No button reads as cancel, go back or "did nothing" when it does something else.
- Confirm before commit, toast after.
- Stay in context, no forced jumps, a way back when leaving.
- Same thing looks the same everywhere (bars, statuses, windows, toasts).
- Plain language, no "(s)", no IDs as explanations, no system errors.
- Only existing NDBX and app components.

### Top problems
1. Fixing a task is a dead end: Task manager has no claim filter, no way back, and no Cancel or Defer, although the blocker asks for them (CL-OV-04).
2. False promise: "The claim can now be closed" after bulk section closure while open tasks still block it, plus a forced jump to Claim overview (CL-SC-07, CL-SC-01).
3. Counts and words do not match: title "Close 4 sections" over a "Close 3 sections" button, "These 1 claim", "2 selected" versus "4 sections selected", and no result toast after bulk closure (CL-SC-02, CL-CL-01).
